1. Understanding the Concept of a Rootkit

A rootkit is a set of malicious instructions designed to conceal the presence of malicious software and often give persistant access to a machine while often surviving reboots. Note that some rootkits technically only live in RAM and might not survive reboots. There are many levels of rootkits targetting different infrastructure, this page will cover the most pertinent ones. Rootkits can run at many different privilege levels. Please note that this document assumes you already have a deep knowledge of computing and how a CPU works. This is not a good article to learn the fundamentals or computing.

The process of infection

After getting code execution as SYSTEM on Windows, either via a malicious installer running privileged or via an exploit, an attacker might want to enable future access on this machine for things like stealing credentials or personal information. One way to do this is by modifying the MBR and this is what this article will focus on.

Different levels of rootkits

As mentionned earlier, attackers have a wide variety of targets when trying to enable persistance in Windows.

  • Bootkit
  • Hypervisor rootkit
  • Firmware rootkit

Traditional Bootkits

Bootkits usually target the MBR (Master Boot Record) and fall in one of those categories:

  1. MBR bootkit: Attackers target the Master Boot Record to redirect code execution before boot to a known payload location in a hidden part of the disk.

    It is important to understand what the MBR actually represents to understand why this kind of attack works. The Master Boot Record represents the first 512 bytes of the disk and contains code to be executed before the operating system actually runs. It also contains the partition table and the boot signature.

    • First step: gain code execution as Administrator/SYSTEM. The reason why such a high level of privilege is required: raw write access to \\.\PhysicalDrive0 is needed, and Windows only hands that to an elevated process.
    • Second step: stashing the real MBR somewhere safe. A valid copy is needed, because we will need to jump to it after executing the payload.
    • Third step: writing the payload somewhere safe aswell. We cannot write it directly in the first 512 bytes of the disk, the MBR, so we will write it somewhere else and jump to it.
    • Fourth step: overwriting sector 0 with the malicious hook. We need to keep the original 4 partition-table entries so the disk still looks normally partitionned and Windows still mounts.

After this, the installation phase is done. Let's take a deep dive into what happens on boot.

On boot

  1. The BIOS loads sector 0. Here is an example of the traditional Microsoft-compatible MBR bootstrap code found on BIOS/MBR installations of Windows: 
       33 C0       xor ax, ax
    8E D0       mov ss, ax         ; stack segment = 0
    BC 00 7C    mov sp, 0x7C00     ; stack grows down from just below our code
    8E C0       mov es, ax
    8E D8       mov ds, ax
    BE 00 7C    mov si, 0x7C00     ; SOURCE = where BIOS put us
    BF 00 06    mov di, 0x0600     ; DESTINATION = 0x0600
    B9 00 02    mov cx, 0x0200     ; count = 512 bytes
    FC          cld                ; copy forward
    F3 A4       rep movsb          ; copy 512 bytes: 0x7C00 -> 0x0600
    50 68 1C 06 CB  push..; retf   ; far-jump to 0000:061C (the copy)
  2. We need to remember that the MBR is only 512 bytes. We get 446 for code/metadata, 64 for the partition table and the last 2 are reserved for the 0x55AA signature. Therefore, any code we place in sector 0 on disk only has 446 bytes to work with at best. This is not enough. The code injected into the MBR is a tiny first-stage loader, whose entire job is to drag the real malicious code (that lives somewhere else on disk, with considerably more space available) into memory and jump to it before booting Windows.
  3. It gets interesting, because the legitimate Windows MBR is ALSO a tiny loader. Its job is to scan the partition table and find the active partition, before transferring execution to it. The bootkit simply adds some instructions before this legitimate loader.
  4. Before diving deeper, let's make sure we understand the essentials. The CPU boots in "real mode", with no memory protection, no operating system. This means any code that is ran here can read/write at any address on addressable memory and touch the hardware directly. Addresses are written segment:offset, and the physical address is segment * 16 + offset. So 0000:7C00 = physical 0x7C00. There is a reason why it jumps to 0x7C00, but this is beyond the scope of this article. It is mainly for compatibility with the older computers.

BIOS interrupts

Interrupt       Service
────────────────────────────────────────────────────────────────
int 10h         Video — print char, set mode
int 11h         Equipment list
int 12h         Conventional memory size
int 13h         Disk — read/write sectors
int 14h         Serial port
int 15h         Misc system — A20 gate, E820h memory map
int 16h         Keyboard
int 18h         Boot failure handler ("no bootable device" / ROM BASIC)
int 19h         Bootstrap loader — (re)load the boot sector
int 1Ah         RTC / time (and PCI BIOS)
  1. We are able to call those BIOS interrupts with barely any code loaded because the BIOS interrupt handlers are available through the firmware before our bootloader even starts executing. When the computer is powered on, the BIOS starts executing code stored in the motherboard's BIOS ROM. Among other things, it initializes the Interrupt Vector Table (IVT). In x86 Real Mode, the first 1KiB of conventional memory is reserved for the IVT. It occupies 256 * 4 = 1024 bytes. Each entry contains a far pointer:
    • 16-bit offset
    • 16-bit segment
    That leaves space for 256 interrupt vectors. Each entry points to the actual code responsible for handling that interrupt. If you read carefully the interrupt table snippet shown above, you might have noticed int 13h that would seem pretty interesting to attackers. We will come back to this later on. Let's continue with the normal boot process on Legacy BIOS.
  2. After validating the partition table, the MBR reads the active partition's first sector. It retrieves the partition's starting location and calls int 13h to read that sector and loads it to 0x7C00. That sector is the VBR (Volume Boot Record). The pattern here is that the MBR is just a hook that finds the right partition and loads the next stage to 0x7C00. On modern Windows (BIOS mode), the active partition is usually a small reserved partition, not C:. It holds the boot file and is usually between 100-500Mb.
  3. After this, the control has been passed to the VBR. One distinction here, the VBR is filesystem-aware. With enough logic now in memory, this code can crawl the filesystem and load the bootmgr file into memory and jump to it. From here, bootmgr switches the CPU to protected mode during its initialization. On 64-bit Windows installations, it also transitions to 64-bit long mode after loading the Windows OS loader (winload.exe).

How a bootkit differs from regular boot

  1. The initial steps are the same. The BIOS loads sector 0 to 0x7C00 and jumps in.
  2. We relocate the stub out of 0x7C00, since the real MBR is expected to run here shortly.
  3. Stub hooks int 13h and saves the original vector at 0x0000:0x004C and writes its own handler address here.
  4. The stub reads the malware payload from the disk into RAM via int 13h, the BIOS interrupt responsible for read/write in Real Mode. It cannot execute directly from disk, so everything needs to be loaded into RAM before jumping there. Once the payload is executed, we just have to chain back to the real MBR after restoring its expected execution location. Normal boot process resumes. We are essentially just adding a step to execute our malware written somewhere on the disk.

At this point, you might think this kind of bootkit would be easily detectable. We just need to inspect the MBR at runtime, and see if it differs from the original MBR. Seems pretty easy, right?

Basic Anti-Detection at Runtime

By default, when something tries to read from disk sector 0 from inside Windows, the flow looks like this:

  • User mode calls ReadFile on a handle to \\.\PhysicalDrive0.
  • That becomes NtReadFile and the I/O manager builds an IRP (I/O Request Packet) with the major function IRP_MJ_READ.
  • The IRP travels down the device stack for \Device\Harddisk0\DR0: the disk class driver (disk.sys) on top all the way down to hardware.
  • The hardware returns the sector, the IRP travels back up, and the bytes land in the caller's buffer.

The bootkit's driver inserts itself into that stack, typically by IoAttachDeviceToDeviceStack, attaching itself as a lower filter below disk.sys. Now every IRP_MJ_READ passes through its code. When a request arrives, it checks two fields:

  1. Parameters.Read.ByteOffset: the disk offset being read.
  2. Parameters.Read.Length: how much is being read.

If ByteOffset = 0 on the system disk, that's a read from the start of Sector 0, which might be an MBR read, and we can poison it. There are two main ways to do so.

  1. Completion-time edit: it registers an I/O completion routine, lets the real read go through to hardware, then in the completion routine, after the true bytes are in the buffer but before control returns to the caller, it overwrites the buffer with the stashed clean MBR. To the caller, nothing suspicious happened.
  2. Redirect: it rewrites the target offset so the read is served from the stashed clean copy somewhere on disk instead of sector 0.

But hiding reads is not enough. A competent bootkit would also hide writes as a method of self-defense against a MBR clean. We could use the same technique to catch a IRP_MJ_WRITE, drop it but still return STATUS_SUCCESS if the write target was sector 0. This would trick a AV repair into saying "MBR repaired" while the infection is still untouched.

  1. VBR/IPL bootkit: Attackers target the Volume Boot Record or Initial Program Loader, specifically to dodge detection via tools that only watch the MBR.
